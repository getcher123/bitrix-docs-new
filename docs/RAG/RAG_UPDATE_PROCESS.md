# Процесс обновления индекса RAG

Этот документ описывает, как обновлять индексы и как фиксируется версия.

## Полное обновление

Использовать при крупных изменениях корпуса или смене модели эмбеддингов.

```bash
bitrix-rag --env-file rag/.env index
```

Что происходит:
- пересоздаются `chunks.jsonl` и `bm25.json`,
- обновляется векторная коллекция в Qdrant,
- перезаписываются `index_manifest.json` и `index_version.json`.

## Инкрементальное обновление

Использовать при регулярных правках нескольких файлов.

```bash
bitrix-rag --env-file rag/.env index --incremental --strategy auto
```

Стратегии:
- `auto` — если есть git, использует `git diff`, иначе `mtime`,
- `git` — только изменения из `git diff --name-only` и untracked,
- `mtime` — сравнение `mtime/size` с `index_manifest.json`.

Что происходит:
- перегенерируются чанки только для измененных файлов,
- BM25 пересчитывается на обновленном наборе чанков,
- Qdrant‑коллекция пересоздается, но эмбеддинги берутся из кеша,
- версия фиксируется в `index_version.json`.

## Версионирование индекса

Файл `.rag/index_version.json` содержит:
- `git_commit` — текущий хэш коммита (если repo под git),
- `built_at` — UTC‑время сборки,
- `incremental` — был ли запуск инкрементальным.

## Рекомендации

- После смены `BGE_PROVIDER` или модели эмбеддингов делайте полный rebuild.
- При нестабильных endpoints используйте `RAG_FAST_REST=1` для REST‑запросов.
